# Experiment protocol

Fixed on 23 Nov 2026, after calibration and before any run that is used in the comparison. This repository holds a single commit, so that order cannot be checked from it (deviation 21). Anything decided later is an "Addition" (sections 12 to 14) or is listed under "Deviations" at the end.

On 24 Nov 2026, after the first session, the comparison at the baseline's rated load (section 14) became the study's main question (deviation 22). Sections 1 to 13 are the protocol of the first session, for the three configurations of the study.

## 1. Configurations

All three run the same container images, the same Aurora MySQL engine version (3.10.6) and parameter group, the same Kubernetes version, the same load balancer and the same database volume. Only instance types, sizes and replica counts change.

| | A: Graviton2 baseline | B: Graviton5, same size | C: Graviton5, right-sized |
|---|---|---|---|
| Web nodes (C family) | 2 x c6g.4xlarge | 2 x c9g.4xlarge | 2 x c9g.2xlarge |
| Web pods | 32 | 32 | 16 |
| API nodes (M family) | 3 x m6g.xlarge | 3 x m9g.xlarge | 3 x m9g.large |
| API pods | 6 | 6 | 3 |
| Database (R family), writer + reader | db.r6g.8xlarge | db.r9g.8xlarge | db.r9g.4xlarge |
| System nodes | 2 x m6g.large | 2 x m9g.large | 2 x m9g.large |
| vCPUs: web / API / database writer | 32 / 12 / 32 | 32 / 12 / 32 | 16 / 6 / 16 |

- **A to B** is the upgrade: same family, same size, newer generation.
- **B to C** is the right-sizing: every tier at half the baseline's vCPUs.

Pod sizes are constant: a web pod requests 0.95 vCPU (Node.js runs JavaScript on one thread); an API pod has a request and limit of 1.75 vCPU and 4 GiB, so the JVM sees two CPUs on every node size. The API's database connection pool is 24 per pod with six pods and 48 per pod with three, so the database sees 144 connections in every configuration.

Order of execution: A, B, C. Each change is a commit that the pipeline applies.

## 2. Workload

One open-loop request stream. Each request is drawn independently from this mix:

| Operation | Share | Path | Tiers exercised |
|---|---|---|---|
| page_home | 6% | `GET /` | web, API, database |
| page_category | 10% | `GET /c/{category}?sort=&page=` | web, API, database |
| page_product | 12% | `GET /p/{product}` | web, API, database |
| page_search | 3% | `GET /search?q=` | web, API, database |
| api_home | 2% | `GET /api/home` | API, database |
| api_catalog | 4% | `GET /api/catalog?category=&sort=&page=` | API, database |
| api_product | 14% | `GET /api/products/{id}` | API, database |
| api_search | 1.5% | `GET /api/search?q=` | API, database |
| api_orders | 14% | `GET /api/customers/{id}/orders` | API, database |
| api_cart_get | 20% | `GET /api/cart/{customer}` | API, database |
| api_cart_put | 9% | `PUT /api/cart/{customer}/items/{product}` | API, database (write) |
| api_order_post | 4.5% | `POST /api/orders` | API, database (write, transaction) |

- 31% of requests are server-rendered pages; each page makes one API call from the web tier.
- 69% are direct API calls, as made by browsers after a page has loaded and by mobile clients.
- 13.5% of requests write to the database.
- Categories, products and customers are chosen with the same skew the data generator used, so popular items receive most of the traffic. A quarter of searches are a single word, which matches about 2.5% of the catalog.
- Every request reaches the database. Nothing is cached except the category list (60 seconds, in the web and API tiers).

Data set: 1,000,000 products in 500 categories, 2,000,000 customers, 8,000,000 orders with 24 million lines, 5,000,000 reviews, 6,000,000 cart lines. About 5.4 GB with indexes, generated by `SeedRunner` from fixed hashes of the row number. It fits in the buffer pool of every database class used, so the database tier is CPU-bound in every configuration. That is a precondition for halving a memory-optimized class and is checked in each run through the buffer cache hit ratio.

Orders written by a run are deleted before the next run. Cart writes update existing rows. Every run therefore starts from the same data.

## 3. Load generation

- Distributed Load Testing on AWS v4.3.4 (an existing deployment in us-west-2), k6 1.5.0 in native run mode.
- Executor: `ramping-arrival-rate`. Requests start on schedule regardless of how long earlier ones take, so a slow system accumulates a queue instead of slowing the test down.
- Load generator tasks: 2 vCPU AWS Fargate tasks in the same Region. Each task runs the script at its share of the total rate. Their CPU is checked after every run; a run is discarded if any minute exceeds 60% of the reserved CPU.
- Request timeout: 5 seconds. A timed-out request counts as a failure.
- Latency is k6's `http_req_duration`. DLT stores one histogram per label and task with 0.5% relative bucket width; `tools/dlthist.py` adds the histograms of all tasks and reads percentiles from the combined distribution.

## 4. Operating load

Calibration on configuration A (see `results/calibration/`) showed CPU cost per request to be constant from 4,000 to 12,000 requests per second.

**Operating load: 8,000 requests per second.** At that rate the baseline's database writer ran at 54% CPU and its web tier at 50%. The API tier ran at 36% on 2 x m6g.2xlarge and was therefore reduced to 3 x m6g.xlarge before the official runs.

The calibration runs are kept in `results/calibration/` and are not part of the comparison:

| Run | Purpose | Request mix |
|---|---|---|
| `smoke1` | Check the toolchain end to end at 600 requests per second | First draft, 45% pages |
| `cal1` | CPU cost per request of each tier at 3,000 requests per second | First draft, 45% pages |
| `cal2` | The same after shifting the mix towards direct API calls | Second draft, 27.5% pages |
| `cal3-cap` | Staircase from 4,000 to 12,000 requests per second | Final, 31% pages |

The mix was changed twice during calibration, for one reason: with the first draft the database needed far more CPU per request than the other tiers, so no fleet of whole instances put all three tiers near half utilization at the same rate. The final mix does. It was frozen before any official run and is the same for every configuration.

## 5. Runs per configuration

In this order, after the pipeline reports the configuration deployed and all pods ready:

1. **Warm-up run, discarded.** Three minutes at half the operating load. Pods restart whenever a configuration is deployed, so the JVMs start cold.
2. **Capacity run.** Staircase of arrival rates, 120 seconds per step, the first 10 seconds of each step discarded. Steps as multiples of the operating load: 1.0, 1.2, 1.4, 1.5, 1.6, 1.7, 1.8, 1.9, 2.0, 2.1, 2.2. For configuration B, which is expected to have about twice the capacity, the steps are 1.0, 1.5, 2.0, 2.5, 3.0, 3.2, 3.4, 3.6, 3.8, 4.0.
3. **Three steady runs** at the operating load: 60 seconds ramp, 10 seconds settle, 590 seconds measured.

A run is repeated if DLT reports it failed, if fewer tasks report than were requested, or if the load generator check fails. Repeats are recorded.

## 6. Measurements

| Measure | Source | Computation |
|---|---|---|
| Achieved rate, errors | k6 through DLT | Requests in the measured window divided by its length; failures are HTTP status 400 or above, timeouts and connection errors |
| Latency mean, p50, p90, p95, p99, p99.9 | k6 through DLT | From the merged histograms |
| Web and API CPU | kubelet `/metrics/resource` on every node, sampled every 15 s | Difference of cumulative CPU-seconds over the measured window, divided by its length. Reported as cores, as a share of the tier's vCPUs, and as CPU milliseconds per request |
| Database CPU | CloudWatch `AWS/RDS` `CPUUtilization`, 1-minute | Mean of the minutes that lie entirely inside the measured window; times vCPUs gives cores |
| Database latency and throughput | CloudWatch `AWS/RDS` | Same window |
| Load balancer | CloudWatch `AWS/ApplicationELB` | Request count, target response time, 5xx from targets and from the load balancer, LCUs |
| Database counters | `SHOW GLOBAL STATUS` before and after | Statements and rows read per request, buffer pool reads |
| CPU throttling | cAdvisor on each node before and after | Share of CFS periods in which an application container was throttled |

## 7. Maximum sustainable throughput

The highest step of the capacity run at which all of these hold:

- achieved rate is at least 99% of the target rate;
- error rate is at most 0.1%;
- p95 latency is at most 50 ms;
- p99 latency is at most 100 ms.

The latency limits are about three to four times the baseline's values at the operating load (p95 17 ms, p99 27 ms in calibration).

## 8. Acceptance criteria

Stated in the study's brief before the system was built. A configuration "sustains the baseline's performance" if, compared with configuration A:

| Criterion | Threshold |
|---|---|
| Achieved request rate at the operating load | At least 99.5% of the target |
| Error rate at the operating load | At most 0.1%, and at most the baseline's rate plus 0.05 percentage points |
| p50 and p95 latency at the operating load | At most 5% above the baseline |
| p99 latency at the operating load | At most 10% above the baseline |
| Maximum sustainable throughput | At least 95% of the baseline's |

Latency and rate at the operating load are compared using the median of the three steady runs, and the spread between runs is reported next to it. Each criterion is reported as met or not met.

## 9. Observing the changes

While the pipeline applies A to B, and again B to C, two DLT tests run for the whole change:

- a background load of 4,000 requests per second (half the operating load, standing in for an off-peak maintenance window);
- a probe of 100 requests per second whose per-request k6 output is kept, giving a second-by-second record of failures.

Reported: failed requests and their share, the periods in which any operation failed, and what CloudFormation, Amazon EKS and Amazon RDS were doing at those times.

## 10. Cost model

- Prices: `results/pricing/us-west-2.json`, taken from the AWS Price List API, the Savings Plans API and the Amazon RDS reserved-instance offerings API on the day of the study.
- Primary view: On-Demand, 730 hours per month, every instance running continuously.
- Secondary view: one-year, no-upfront commitments where AWS publishes one for the instance type.
- Usage-priced items that do not depend on the processor (Aurora I/O, load balancer capacity units, data transfer) are priced from the quantities measured at the operating load and are the same in every configuration.
- Derived: monthly cost, cost per million requests at the operating load, and requests per dollar at maximum sustainable throughput.

## 11. Known limits, fixed in advance

- One Region, one day, one workload. Three steady runs per configuration measure run-to-run noise, not day-to-day variation.
- The data set fits in memory. A workload whose working set exceeds half of the baseline's memory cannot halve an R-family class regardless of processor speed.
- The baseline is calibrated to this workload. A baseline with spare capacity would right-size further; one that is already saturated would not sustain the operating load at all.
- No JVM, Node.js, kernel or database tuning is applied in any configuration, beyond one container heap-sizing flag (`-XX:MaxRAMPercentage=70`).
- The load balancer listens on HTTP. TLS termination at the load balancer does not run on the instances being compared.
- Configurations run one after another on the same cluster and database, not side by side.

## 12. Addition: capacity at a CPU ceiling

Added on 23 Nov 2026 at 18:18 UTC at the owner's request. At that time configuration A's runs were complete and analysed, the change from A to B had been applied, and the load of B's warm-up run had ended 23 seconds earlier; its result was printed three minutes later. No result of a benchmark run of B or C had been seen, and nothing recorded on Graviton5 during the change had been analysed for performance. The rule below was therefore written knowing A's results and nothing else.

Why: the operating load of section 4 was chosen as the rate at which the baseline's tiers are about half busy. That is a judgment, not a rule. The owner's rule is the one many operators use: a tier above 80% CPU is treated as overloaded, and the remaining 20% is the buffer. Stating each configuration's capacity at that ceiling makes the comparison independent of how much spare capacity the baseline happened to have at 8,000 requests per second.

Definitions:

- **CPU ceiling**: 80% utilization of a tier.
- **Utilization**, measured against the CPU the tier is allowed to use:
  - web: CPU in use on the web nodes divided by their vCPUs (kubelet counters, as in section 6);
  - API: CPU in use on the API nodes divided by the sum of the API pods' CPU limits (1.75 vCPU per pod: 10.5 in A and B, 5.25 in C). The limit, not the node size, is what the tier can use. The share of node vCPUs is reported next to it;
  - database: CloudWatch `CPUUtilization` of the writer.
- **Rated capacity**: the request rate at which the busiest tier is at 80%, provided the latency and error limits of section 7 still hold at that rate. If those limits are reached first, the rated capacity is the maximum sustainable throughput and the table says so.

Procedure for each configuration, after its steady runs:

1. **Estimate.** From the capacity run, the lowest rate at which any tier reaches 80%, by linear interpolation between the steps on either side, rounded down to a multiple of 100 requests per second.
2. **Ceiling run.** One steady run at that rate: 60 seconds ramp, 10 seconds settle, 590 seconds measured, the same script, and load generator tasks in proportion to the rate (one task per 286 requests per second, as in the steady runs).
3. **Rated capacity** = the rate of the ceiling run x 80 / the utilization, in percent, of the busiest tier in that run. If that utilization is outside 75% to 85%, the run is repeated at the corrected rate and the repeat is recorded.

Configuration A had been replaced when this was added. Its estimate comes from data recorded earlier: its capacity run and the calibration staircase both put the database writer at 80% at about 11,850 requests per second, with the web tier at about 73% and the API tier at about 75% of its limit. To measure A the same way as the others, A is deployed again at the end of the session ("A again"), and gets a ceiling run plus one steady run at the operating load. The second shows whether the baseline's results reproduce at the end of the day.

Reported for every configuration: rated capacity, the tier that limits it, latency and errors in the ceiling run, and the On-Demand monthly cost for each 1,000 requests per second of rated capacity.

Question and decision rule, fixed before any benchmark result of B or C: does the right-sized Graviton5 configuration (C) have a rated capacity at least as high as the baseline's (A), at a lower cost? It is "yes" if C's rated capacity is at least A's. If not, the shortfall is reported as measured, next to the cost per unit of rated capacity.

## 14. Addition: the comparison at the baseline's rated load (second session)

Added on 24 Nov 2026 at 08:14 UTC, at the owner's request and after a review of the method by two reviewers on other models. At that time every run of the first session was complete and analysed, the stack had been parked for four hours, its database cluster was starting again, and no run of the second session had started. What follows was therefore written knowing the first session's results and none of the second's.

Why: the operating load of section 4 was a judgment. The owner's rule sets the load by the baseline itself: the request rate at which the baseline's busiest tier is at the 80% CPU ceiling of section 12. The configurations are then compared at that one rate, and what is left of each configuration's own ceiling is its headroom.

- **Comparison load: 11,800 requests per second.** It is the rate of the baseline's ceiling run of the first session (`a2-ceiling`), in which the baseline's busiest tier was at 79.4% CPU utilization by the rule of section 12 and its rated capacity came out as 11,900 requests per second.
- **Runs.** The script, request mix and measurement are those of section 5: 60 seconds ramp, 10 seconds settle, 590 seconds measured, 42 load generator tasks.
  - Configuration A, as it was parked: a warm-up, then two runs (`a3-rated-1`, `a3-rated-2`). With `a2-ceiling` that makes three runs at this rate. The two new runs follow a stop and start of the database cluster and run on new nodes and pods; they are reported next to the first one, not pooled silently.
  - The change from A to C is applied through the pipeline, pods first, and is not observed under load.
  - Configuration C: a warm-up, then three runs (`c2-rated-1` to `c2-rated-3`), then one run at 8,000 requests per second (`c2-r1`) to compare this deployment with the first session's.
  - Configuration B is not deployed again. Its figures at this rate come from the step of its capacity run at 12,000 requests per second (110 seconds) and are labelled as such.
- **What is compared.** Achieved rate, error rate, p50, p95 and p99 response time, the CPU utilization of each tier as defined in section 12, and CPU milliseconds per request: the median of a configuration's three runs, with the lowest and highest next to it.
- **Decision rule, fixed before any run of this session.** The right-sized Graviton5 configuration carries the baseline's rated load if, at 11,800 requests per second, it meets the criteria of section 8 against configuration A at the same rate (achieved rate at least 99.5% of the target; error rate at most 0.1% and at most the baseline's plus 0.05 percentage points; p50 and p95 at most 5% above the baseline's; p99 at most 10% above), and none of its tiers is above 80% CPU utilization. Each criterion is reported as met or not met.
- **What the first session leads me to expect**, stated so that it can be checked: interpolated between the steps of C's capacity run at 11,200 and 12,000 requests per second, C's busiest tier is at about 65% CPU utilization at this rate and its p99 response time is about 16.5 ms.
- **Headroom.** Each configuration's rated capacity at the ceiling is the first session's (section 12); it is not measured again.
- **One web node out of service.** After C's runs, one of its two web nodes is cordoned and its web pods are deleted; their replacements find no room on the other node and stay pending. One run at 8,000 requests per second follows (`c2n-r1`). Reported: achieved rate, error rate, response times, and the CPU utilization of the web node that is left. It counts as held if the limits of section 7 are met. A drain is not used: it would stop at the pod disruption budget, which a lost node does not. No run with a node out of service is made at the comparison load: with two web nodes at up to 80% CPU utilization, one node would need up to 160%.

## Deviations

Numbered in the order in which they were first recorded. What was added to one of them later is dated there. Times are UTC, on 23 Nov 2026 unless a date is given.

1. **Environment snapshot while a run was being prepared (16:02).** `scripts/snapshot-environment.sh` ran `java -version` and a short Node.js command in one API pod and one web pod at 16:02:22, while the load generators of run `a-r1` were being provisioned. That is 70 seconds before the load started and before the measured window (16:04:41 to 16:14:31). For later configurations the snapshot runs before the warm-up.
2. **Observation of the A to B change restarted (16:57 to 17:04).** The first launch of the observation tests ended when the shell that started them was closed. Tests `gu-ab-load-11231657` and `gu-ab-probe-11231657` were cancelled before the change was pushed, and the observation was started again as `gu-ab-load-11231702` and `gu-ab-probe-11231702`. Nothing had been changed in between.
3. **Sections 12 and 13 added (18:18:08, commit `02fe569`)**, as described there. The sentence in section 12 about what was known at the time was made more precise in commit `9e9ac1b` (19:44), after B's steady runs; the rule itself was not changed. For the record of what existed at 18:18: B's warm-up load had ended at 18:17:45 and its result was printed at 18:21:09; Graviton5 instances had served the observation load of the A to B change since about 17:34, and that data had not been analysed for performance.
4. **Deployed-state listing during a warm-up (18:11), repeated between runs (19:23).** `scripts/capture-evidence.sh` ran during configuration B's warm-up run, which is discarded. It reads from the Kubernetes and AWS control planes only. The listing kept in the repository is a second recording, made at 19:23 between runs `b-r2` and `b-r3` with a narrower node listing; nothing had changed in between.
5. **Timing of Aurora's CloudWatch datapoints (found at about 18:15, before section 12 was written; applies to every configuration).** Section 6 takes database CPU as the mean of the one-minute datapoints whose timestamps lie inside the measured window. Reading the baseline's data against the 80% rule showed that a datapoint of the baseline's writer describes the 60 seconds that begin about 43 seconds before its timestamp. The end of every steady run shows it: the load stops at a known second, and the CPU datapoints fall one step late. On the Graviton5 instances the offset is about 1 second, so it belongs to the instance, not to the service. The analysis now measures the offset for each configuration from the end of its steady runs, and assigns each Aurora datapoint to the interval it covers (`analysis/summarize.py`). Effect on configuration A: the steady runs are unchanged to one decimal (56.7%). The capacity run's database CPU per step, which had mixed each step with the one before it, rises by 2 to 6 points (78.4% to 80.8% at 12,000 requests per second). Load balancer and EC2 datapoints have no such offset. Latency, error and throughput figures do not use CloudWatch. Order of events: the offset was seen in the raw datapoints at about 18:15; section 12, committed at 18:18:08 (`02fe569`), therefore already quotes the corrected estimate of about 11,850 requests per second for the baseline; the corrected analysis code was committed at 18:23:42 (`2ef96f8`). Read by timestamp, the baseline's writer would reach 80% at about 12,300 requests per second, so the correction lowers the rated capacity that configuration C is compared with by about 3.6%. The baseline's ceiling run, made when A is deployed again, measures that capacity over ten minutes and does not depend on the correction.
6. **API pod logs read between two runs (19:05:48 to 19:07:14).** To see what the API pods logged during the two database failovers of the A to B change, `scripts/capture-failover-logs.sh` read their logs through the kubelet. It ran after the load of run `b-r1` had ended (19:04) and before the load generators of `b-r2` were provisioned (19:08), so no load was running. The pods that served the second half of that change are the ones configuration B is benchmarked on, which is why their logs still covered both failovers. Kubernetes had already discarded the events of that hour; from the B to C change on, `scripts/change-stage.sh` saves them as soon as the pipeline finishes.
7. **Observation of the B to C change limited to one hour (20:02 to 20:05).** The first launch asked for observation tests of 4,500 seconds, to leave room for the two pipeline runs this change needs. Distributed Load Testing on AWS rejected them: a test may hold its load for at most 3,600 seconds. Nothing had been changed. The observation was started again with 3,600 seconds, and the undisturbed lead-in before the first push was shortened from 180 to 60 seconds so that both pipeline runs fit.
8. **Configuration B's capacity run did not reach its limit.** The steps fixed for B in section 5 end at four times the operating load, 32,000 requests per second. B passed all of them. Its maximum sustainable throughput is therefore reported as "at least 32,000". The run was not extended.
9. **Placement of the API nodes relative to the database writer (noticed in review at 20:25).** Amazon EKS spreads the three API nodes over two Availability Zones as 1 + 2, and the writer is in one of the two zones. Every API request makes two to three round trips to the writer, and a round trip within a zone is shorter. By chance, one of the three API nodes shared the writer's zone during configuration A's runs, and two of three during configuration B's. Response times of A and B are therefore compared across different placements; CPU per request and capacity are not affected in the same way. From here on the placement is made the baseline's: after a change, `scripts/align-writer-zone.sh 1` fails the writer over if it is not in the zone that holds one API node. Configuration C had the baseline's placement without a failover. When A is deployed again it is measured in the baseline's placement (steady run and ceiling run) and then, after a failover, in B's placement (one steady run, `a2p-r1`), which shows what the placement alone changes on the same hardware.
10. **Aurora I/O is priced per configuration (20:50).** Section 10 says that usage-priced items, Aurora I/O among them, are priced from quantities measured at the operating load and are the same in every configuration. For I/O that could not be done, and the assumption does not hold exactly. CloudWatch publishes the billed count (`VolumeWriteIOPs`) as an average over blocks of about an hour, which cannot be assigned to a run. The number of write I/Os a request causes also falls as load rises, because the engine batches more, and it is a few percent higher on the faster instances. The bill therefore takes, for each configuration, the writer's storage write operations per second during the warm-up run (4,000 requests per second, the average load the bill assumes) from Enhanced Monitoring, multiplied by the ratio of billed write I/Os to write operations over the whole study (`analysis/usage.py`). Read I/O is zero in every run because the data set is served from memory. Load balancer capacity units and data transfer are priced as section 10 says; the capacity units CloudWatch reports for the baseline's steady runs (116.5 per hour) agree with the model (1 unit per GB processed per hour).
11. **What the throughput criterion can resolve.** The criterion of section 8 is 95% of the baseline's maximum sustainable throughput, which is 13,680 requests per second. The capacity steps have no step at that rate: the nearest are 13,600 and 14,400. A configuration on the standard steps therefore has to pass 14,400, the baseline's own figure, to meet the criterion.
12. **Wording of sections 1, 4 and 7, as applied.** Section 1 says "every tier at half the baseline's vCPUs"; that is the web, API and database tiers, the two system nodes keep their size. Section 4 calls the CPU cost per request "constant" from 4,000 to 12,000 requests per second; it falls slightly with load, by 7% for the database writer over that range. Section 7 defines maximum sustainable throughput as the highest step at which all limits hold; the analysis takes the highest step of the unbroken run of passing steps from the start, which is the same step in every capacity run of this study. Section 8 names latency and rate as the measures compared on the median of the steady runs; the error rate is compared the same way. Section 2 gives the data set as about 5.4 GB with indexes; the table and index sizes the database reports add up to 5.68 GB, which is 5.29 GiB (`results/evidence/data-size.txt`). Section 3 says a run whose load generators exceed 60% of their reserved CPU is discarded and section 5 says it is repeated; both apply, and no run reached the limit: the check divides the highest per-minute CPU of any one task by the task's reservation.
13. **Rated capacity when a ceiling run does not confirm the estimate (22:08).** Section 12 says that if the latency and error limits are reached before any tier is at 80%, the rated capacity is the maximum sustainable throughput. Two reviewers pointed out that this can over-rate a configuration: if its 10-minute ceiling run breaks the limits, the highest passing step of its staircase may lie above the rate that run just failed to hold. Section 12 also does not say what happens if the repeat of a ceiling run is still outside 75% to 85%. As applied from here on:
    - a ceiling run counts only if it completed with its busiest tier between 75% and 85%. If none does, the configuration keeps the estimate interpolated from its capacity run, and the table says that the ceiling run was not used;
    - if a ceiling run that counts breaks the latency or error limits of section 7, the configuration gets no rating, and the rate of that run is reported as an upper bound;
    - if a staircase passes every step without any tier reaching 80%, the configuration gets no rating from it, and its highest step is reported as a lower bound;
    - if a step of the staircase breaks the limits before any tier is at 80%, the rated capacity is the highest passing step, as section 12 says;
    - rated capacities are reported rounded to 100 requests per second, because a ceiling run is one run and a staircase step has one one-minute database datapoint. The question of section 12 is decided on the unrounded figures. The baseline's interpolated estimate, 11,857, was written as "about 11,850" in section 12 and is reported as 11,900 until its ceiling run replaces it.
